# Post-v0.6.0 Roadmap — agent-governance-core

**Date:** 2026-04-16
**Current version:** v0.6.0 (Phase 3 Track 2.2 Circuit Breaker shipped)
**Deployment context (confirmed):** internal / controlled, single-tenant pilot (NOT multi-tenant from day one)
**Load target (confirmed):** unknown — baseline is a discovery goal, not a validation goal

---

## Why this order

Six tracks have been stacked on top of each other (MVP → observability → adaptive routing → scalability → DLQ → breaker). Before connecting more automation, the system needs to be **proven operable under real conditions**. Everything after Phase 3.5 becomes more valuable and lower-risk once we have measured behaviour, dashboards, and runbooks.

## Phase order (default)

1. **Phase 3.5 — Hardening** (operability baseline)
2. **Phase 4 — Breaker → Adaptive Routing feedback loop** (use the signal)
3. **Phase 5 — Approvals UX / HITL surface** (close domain gap)
4. **Phase 6 — Security / Multi-tenancy / AuthZ** (deferred — not needed for 1-tenant pilot)

Phase 6 jumps to #1 the moment deployment context changes to multi-tenant or external-facing.

## Phase 3.5 — Hardening

Goal: prove v0.6.0 is operable. Four sub-tracks, sequential, each with an explicit close criterion.

### 3.5.A — Load baseline (3–4 days)

**Purpose:** discover real baseline behaviour. No SLOs yet.

**Scope:**
- k6 scripts for three critical flows:
  - Happy path: `submit → route → evaluate → start → N attempts → complete`
  - DLQ flow: force retries until budget exhaustion + quarantine
  - Breaker flow: force consecutive failures on a (tool, role) pair
- Measurements per flow:
  - Throughput (req/s sustained)
  - Latency percentiles: P50, P95, P99
  - pg connection pool utilization + saturation point
  - Memory + goroutine growth over time

**Closes when:**
- Documented numbers: "current system sustains X req/s with P99 < Y ms on Z pg connections; saturates at W req/s"
- k6 scripts committed under `test/load/`
- Findings written up in `docs/observability/baseline-v0.6.0.md`

### 3.5.B — Observability SLOs + dashboards (3–4 days)

**Purpose:** turn baseline numbers into explicit SLIs/SLOs + operational surfaces.

**Scope:**
- Grafana dashboards exposing governance golden signals:
  - Intake rate
  - Routing decisions/s (by outcome)
  - Policy denials by reason
  - DLQ size + quarantined workflows
  - Breaker transitions + current open breakers
  - Workflow state distribution
  - Attempt success/failure ratio by (tool, role)
- SLOs derived from 3.5.A data (realistic, not aspirational):
  - Example shape: `submit P99 < 200ms`, `breaker signal latency < 5s`, `audit write success > 99.9%`
- Alerting rules (minimal): SLO burn rate + DLQ growth + breaker open count

**Closes when:**
- Dashboards versioned as JSON under `docs/observability/grafana/`
- SLIs + SLOs documented in `docs/observability/slos.md`
- Alert rules in `docs/observability/alerts/`

### 3.5.C — Chaos scenarios (4–5 days)

**Purpose:** verify failure modes match expectations.

**Scope — matrix of failure × expected behaviour × verification:**
- pg down mid-workflow — what happens to active leases?
- pg connection pool exhaustion — do we degrade gracefully?
- notifier callback returns 500 / times out
- memory-engine timeout
- container SIGKILL during `workflow_running`
- network partition between governance and pg
- audit writer backlog

**Closes when:**
- Matrix documented in `docs/chaos/scenarios.md`
- Each scenario has: trigger, expected behaviour, actual observed behaviour, test reference
- Any discovered bugs filed with repro tests

### 3.5.D — Runbook (2–3 days)

**Purpose:** make the system operable by a human who has not read the code.

**Scope:**
- Incident escalation paths by type (data corruption, policy drift, runaway retries, mass quarantine, breaker storm)
- Kill switch: when to pull, how, rollback path
- DLQ drainage procedure (manual requeue vs discard)
- Breaker diagnostics + forced reset procedure
- Lease cleanup after pg recovery
- On-call checklist

**Closes when:**
- `docs/runbook.md` written
- Dry-run executed by a reviewer who has not touched the code recently
- Any gaps surfaced during dry-run fixed

**Total Phase 3.5: ~2 weeks.**

## Phase 4 — Breaker → Adaptive Routing feedback loop

**Prerequisite:** Phase 3.5 closed. Do NOT start before.

**Conceptual question to close first (ADR):**
Today the breaker is *signal-only* — it does not influence execution. Consuming breaker state in the router changes that contract. This must be an explicit architectural decision, not a silent wiring.

**Scope (provisional):**
- ADR: "Breaker as input to routing" — scope, rollback, kill switch
- Router reads current breaker state for (tool, role) candidates
- Policy: de-prioritize / skip candidates with OPEN breaker
- Observability: routing decision audit must cite breaker state as a factor
- Integration tests: breaker OPEN → router avoids that candidate

**Estimated size:** ~1 week.

---

## Phase 5 — Approvals UX / HITL surface

**Prerequisite:** Phase 4 closed (or parallel if team capacity allows).

**Scope (provisional):**
- HTTP endpoints: `GET /approvals`, `POST /approvals/:id/approve`, `POST /approvals/:id/reject`
- SDK: `ListApprovals`, `Approve`, `Reject`
- Audit trail for approval actions (actor, timestamp, reason)
- Workflow state transition on approval outcome
- Integration tests end-to-end

**Estimated size:** ~1–2 weeks.

---

## Phase 6 — Security / Multi-tenancy / AuthZ

**Prerequisite:** deployment context changes to multi-tenant OR external-facing. Deferred for single-tenant pilot.

**Scope (when triggered):**
- Tenancy model decision (row-level vs schema-level vs db-level)
- API authentication (mTLS vs JWT vs both)
- RBAC for approvals and admin endpoints
- Audit log per-tenant isolation
- Rate limiting per tenant

**Estimated size:** ~2–3 weeks.

## Decisions log

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Hardening before new features | Six stacked tracks need validation under real load before more automation |
| D2 | Load baseline is discovery, not validation | No target load known yet; measure first, set SLOs from data |
| D3 | Single-tenant pilot assumption | Defers Phase 6 to when deployment context actually needs it |
| D4 | Breaker→Adaptive requires explicit ADR | Changes breaker from "signal-only" to "influences behaviour" — not a silent wiring |
| D5 | Phase 3.5 split into 4 sub-tracks with close criteria | "Hardening" as a single bucket becomes a procrastination graveyard |

## What changes this roadmap

This document is rewritten — not patched — when any of these happen:

- Deployment context shifts (multi-tenant, external-facing, regulated data)
- Real operational incident reveals a gap the roadmap does not address
- A stakeholder requirement (legal, security, SLA) forces a reorder
- Phase 3.5 findings invalidate assumptions (e.g. "baseline too low, need rearchitecture before Phase 4")
